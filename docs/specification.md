# 천안오성고 행사 통합 웹사이트 개발 명세서

**문서 버전:** 1.0<br>
**작성일:** 2026.10.27.<br>
**상태:** 개발 착수 전 초안<br>
**개발 원칙:** 기능 구현 → 테스트 및 안정화 → 디자인 개선

---

## 1. 프로젝트 개요

### 1.1. 목적

천안오성고등학교에서 진행할 2개의 행사 부스를 하나의 웹사이트로 운영한다.

**부스 1 — 타자 대회**

천안오성고등학교 관련 문구를 빠르고 정확하게 입력하는 타자 대회를 진행한다. 입력 속도를 측정하고 오타에 따른 감점을 적용하여 최종 점수를 산출한다. 대회 종료 후 기록을 정리하여 상품 지급에 활용한다.

**부스 2 — 신입생 대상 학교 홍보 글 작성**

재학생이 2027학년도 입학생을 대상으로 천안오성고등학교를 소개하는 글을 작성한다. 제출된 글은 데이터베이스에 저장하고, 운영진의 검토를 거쳐 2027학년도 입학식에서 QR코드로 공개한다.

### 1.2. 기본 원칙

1. 최초 개발에서는 기능의 정확성과 안정성을 최우선으로 한다.
2. UI는 별도의 장식 없이 최소한의 HTML·CSS로 구현한다.
3. 기능 구현이 완료된 이후 전체 디자인을 개선한다.
4. 디자인 개선 과정에서 핵심 비즈니스 로직과 DB 구조를 변경하지 않는 것을 원칙으로 한다.
5. 기능에 불필요한 외부 서비스와 라이브러리의 도입을 최소화한다.
6. 배포 후에도 행사 운영과 2027학년도 입학식에 필요한 기능을 유지할 수 있어야 한다.

### 1.3. 확정된 요구사항

- 하나의 웹사이트에서 2개 부스를 운영한다.
- 타자 대회 문구는 코드에 고정한다.
- 오타 1개당 타수 점수 20점을 차감한다.
- 타자 대회 종료 후 상품 지급을 위한 기록을 정리한다.
- 홍보 글은 데이터베이스에 저장한다.
- 제출한 글을 취합·검토할 수 있어야 한다.
- 2027학년도 입학식에서 QR코드로 홍보 글을 공개한다.
- 디자인 작업은 기술 구현 이후에 진행한다.

## 2. 기술 스택

| 구성 | 선정 기술 |
|---|---|
| 프런트엔드 | React + TypeScript |
| 빌드 도구 | Vite |
| 스타일링 | 기본 CSS |
| 웹 호스팅 | Cloudflare Pages |
| 백엔드 | Cloudflare Pages Functions |
| 데이터베이스 | Cloudflare D1 (SQLite) |
| 타자 기록 임시 저장 | IndexedDB |
| 데이터 내보내기 | CSV / JSON |
| 관리자 인증 | 서버 측 인증 |
| 버전 관리 | Git + GitHub |

### 2.1. 기술 선택 이유

React 기반으로 각 기능을 컴포넌트화하여 개발한다.

타자 엔진, 점수 계산, 데이터 저장, 관리자 기능, 화면 렌더링을 분리하여 추후 디자인을 변경하더라도 기능 로직에 미치는 영향을 최소화한다.

Cloudflare D1은 홍보 글의 영구 저장 용도로 사용한다.

타자 대회 문구와 계산 로직은 프런트엔드에 고정하고, 대회 기록은 행사 기기의 IndexedDB에 저장한 후 CSV로 내보낸다.

**데이터베이스에는 홍보 글과 그 검수 정보만 저장한다.**

### 2.2. 외부 오픈소스 활용

기존 React 기반 한글 타자 연습 프로젝트를 참고할 수 있다.

다만 전체 프로젝트를 그대로 가져오기보다는 한글 입력 및 타자 판정 로직의 재사용 가능성을 검토한다.

외부 소스 채택 전 다음 사항을 확인한다.

- 라이선스 및 재배포 조건
- 한글 IME 호환성
- 타수 계산 방식
- 오타 판정 방식
- 현재 프로젝트와의 의존성 충돌

검증 결과 부적합하면 타자 엔진을 별도로 구현한다.

## 3. 전체 사이트 구조

### 3.1. 페이지 구성

| 경로 | 기능 |
|---|---|
| `/` | 행사 메인 페이지 |
| `/typing` | 타자 대회 |
| `/typing/results` | 타자 대회 기록·순위 관리 |
| `/write` | 홍보 글 작성 |
| `/write/complete` | 제출 완료 |
| `/welcome` | 2027학년도 신입생용 공개 페이지 |
| `/admin` | 관리자 페이지 |

실제 라우팅 방식은 React Router 등으로 구현할 수 있다.

### 3.2. 운영 단계

**Phase A — 행사 진행**

- 타자 대회 활성화
- 홍보 글 작성 및 제출 활성화
- 관리자 검수 기능 사용 가능

**Phase B — 행사 종료**

- 타자 대회 비활성화
- 홍보 글 신규 제출 차단
- 제출된 글은 유지
- 관리자 검수 및 내보내기 기능 유지

**Phase C — 입학식 공개**

- 승인된 글을 신입생 페이지에 게시
- QR코드를 통한 모바일 열람 제공
- 일반 사용자의 글 작성 기능은 비활성화

운영 단계는 서버 환경 설정 및 정적 설정값으로 제어하며, 해당 단계와 무관하게 DB 데이터를 유지한다.

## 4. 부스 1 — 타자 대회

### 4.1. 기본 기능

**FR-T01. 타자 문구**

- 타자 문구는 소스 코드에 상수로 저장한다.
- 초기 버전에서 관리자 문구 편집 기능은 구현하지 않는다.
- 모든 참가자에게 동일한 문구를 제공한다.
- 문구 변경 시 기존 기록과 구별할 수 있도록 문구 버전을 관리한다.

**FR-T02. 참가자 식별**

- 대회 시작 전 참가자 식별 정보를 입력한다.
- 기본안은 참가번호와 표시용 이름이다.
- 동일한 이름을 가진 참가자를 구분할 수 있어야 한다.
- 학번과 같은 개인정보는 필수 수집하지 않는다.

**FR-T03. 타자 입력**

- 정해진 문구를 입력한다.
- 한글 두벌식 입력을 정상적으로 처리해야 한다.
- 입력 위치와 정오 여부를 확인할 수 있어야 한다.
- Backspace를 통한 오타 수정이 가능해야 한다.
- 복사·붙여넣기 방식의 입력은 차단한다.
- 문구를 정확하게 완성하면 자동 종료한다.

**FR-T04. 시간 측정**

- 참가자의 입력 시작부터 문구 완성까지 경과 시간을 측정한다.
- 단조 증가 시계(`performance.now()`)를 사용한다.
- 측정 중 새로고침 또는 페이지 이탈이 발생하면 해당 시도를 중단 처리한다.
- 완성하지 못한 시도는 공식 순위에 포함하지 않는다.

### 4.2. 타수 계산

기본 계산식은 다음과 같다.

`타수 = 기준 타건 수 × 60 / 소요 시간(초)`

기준 타건 수는 타자 문구를 입력하기 위해 필요한 두벌식 기준 타건 수다.

한글 글자 수와 실제 타건 수는 다르므로, 문구를 확정할 때 기준 타건 수를 계산해 상수로 저장한다.

예를 들어 문구 설정은 다음 항목으로 구성한다.

- `challengeId`: 문구 고유 버전
- `text`: 타자 문구
- `referenceKeystrokes`: 기준 타건 수

화면에 표시되는 타수는 정해진 반올림 규칙에 따라 정수로 처리한다.

**주의:** 실제 타건 수를 계산하는 방식, 문장부호·공백 처리와 시작 시점은 구현 전 확정이 필요하다.

### 4.3. 오타 판정

**FR-T05. 오타 누적**

오타는 최종 점수에 감점을 적용하기 위한 누적 횟수로 관리한다.

초기 구현 제안은 다음과 같다.

- 잘못된 문자를 입력하면 오타를 1회 기록한다.
- 해당 문자를 수정해도 이미 기록된 오타는 유지한다.
- 정상적인 Backspace 작업만으로 오타가 증가하지 않는다.
- 한글 조합 중 발생하는 임시 문자 변화는 오타로 계산하지 않는다.
- 하나의 잘못된 문자 입력이 중복해서 계산되지 않아야 한다.
- 잘못 입력한 문자를 수정하여 원문과 일치시켜야 완료할 수 있다.

**오타 수정 시 감점 유지 여부는 아직 확정된 규칙이 아니므로 최종 결정 전까지 잠정안으로 취급한다.**

### 4.4. 한글 IME 처리

다음 이벤트를 고려한다.

- `compositionstart`
- `compositionupdate`
- `compositionend`
- `beforeinput`
- `input`

한글 조합 중에는 중간 문자열이 계속 변화할 수 있다.

따라서 단순 `keydown` 횟수나 `input` 이벤트 횟수를 오타 횟수로 사용하지 않는다.

IME 조합이 확정된 이후 입력 문자열의 변경 사항을 분석하여 오타를 판정한다.

별도의 입력 분석 모듈을 두어 다음 기능을 담당하도록 한다.

- 입력 문자열 관리
- 원문과 입력문의 비교
- 한글 조합 상태 추적
- 오타 이벤트 관리
- 완료 조건 판정

타수 계산 및 점수 계산과 입력 판정 로직은 분리한다.

### 4.5. 최종 점수

**확정 규칙**

`최종 점수 = 타수 - (오타 횟수 × 20)`

예시:

| 타수 | 오타 | 최종 점수 |
|---|---|---|
| 500 | 0 | 500 |
| 500 | 1 | 480 |
| 500 | 3 | 440 |
| 450 | 2 | 410 |

음수 점수 처리와 동점 처리 기준은 개발 전 확정한다.

점수 계산은 별도 순수 함수로 구현하여 단위 테스트할 수 있도록 한다.

### 4.6. 결과 저장

**FR-T06. 로컬 기록 저장**

대회 결과는 행사 기기의 IndexedDB에 저장한다.

저장 항목:

| 필드 | 설명 |
|---|---|
| `id` | 기록 고유 ID |
| `participantId` | 참가번호 |
| `displayName` | 표시용 이름 |
| `challengeId` | 문구 버전 |
| `elapsedMs` | 완료까지 걸린 시간 |
| `speed` | 계산된 타수 |
| `errors` | 오타 횟수 |
| `score` | 최종 점수 |
| `completedAt` | 완료 시각 |

기록은 완료 직후 저장하고, 저장 성공 여부를 확인한 뒤 다음 참가자를 받을 수 있어야 한다.

### 4.7. 기록·상품 관리

**FR-T07. 기록 관리**

- 전체 참가 기록 조회
- 점수순 정렬
- 참가번호·이름 검색
- 중복 참가 기록 확인
- CSV 다운로드
- 상품 수령 여부 기록

상품의 구체적 종류와 지급 기준은 추후 확정한다.

상품 수령 상태 역시 행사 기기에 로컬 저장한다.

**제약 사항**

여러 기기를 동시에 사용할 경우 각 기기의 기록이 자동으로 합쳐지지 않는다.

여러 기기를 운영한다면 기록 파일을 내보내 취합해야 한다.

따라서 최초 구현은 단일 운영 기기를 기준으로 한다.

## 5. 부스 2 — 홍보 글 작성

### 5.1. 기능 개요

재학생이 2027학년도 신입생에게 전달할 천안오성고등학교 소개 글을 작성한다.

제출된 글은 즉시 DB에 저장하고, 관리자 승인 전까지 외부에 공개하지 않는다.

### 5.2. 작성 폼

**FR-W01. 글 작성**

필수 입력 항목:

- 본문
- 공개 동의

선택 입력 항목:

- 작성자 별명

작성자 별명을 입력하지 않으면 기본 표시명인 '오성고 선배'를 사용한다.

초기 구현에서는 글 유형 분류, 사진 첨부, 댓글, 좋아요 기능을 제외한다.

**글 길이의 잠정 기준**

- 최소 10자
- 최대 700자
- 줄바꿈 허용
- 공백만으로 구성된 글 제출 불가

글자 수는 유니코드 문자 단위를 기준으로 검사하고, 서버에서도 동일한 기준을 적용한다.

### 5.3. 제출 처리

**FR-W02. DB 저장**

제출 순서:

1. 작성자가 글을 입력한다.
2. 클라이언트에서 입력값을 검증한다.
3. 서버에 POST 요청을 전송한다.
4. 서버에서 제출 가능 상태와 입력값을 다시 검증한다.
5. 유효하면 D1에 저장한다.
6. 저장 성공 응답을 받은 경우에만 완료 화면을 표시한다.

DB 저장에 실패했는데 성공으로 표시하는 상황이 발생해서는 안 된다.

### 5.4. 중복 제출 방지

**FR-W03. 중복 요청 처리**

- 제출 버튼 연속 클릭 방지
- 요청 처리 중 중복 제출 차단
- 각 제출 시도에 고유 요청 ID 부여
- 네트워크 오류 후 동일 요청 재전송 시 중복 레코드가 생성되지 않도록 처리

이를 위해 서버에서 `submission_key`를 고유하게 관리한다.

단, 서로 다른 제출 요청에 같은 글이 포함되는 것까지 자동으로 중복 판정하지는 않는다.

### 5.5. 제출 실패 처리

서버 오류 또는 네트워크 단절 시:

- 입력된 글을 삭제하지 않는다.
- 오류 메시지를 표시한다.
- 재시도할 수 있어야 한다.
- 서버가 저장했으나 응답만 유실된 경우에도 중복 저장되지 않아야 한다.

공용 부스 기기에서는 다른 참가자가 이전 작성자의 글을 볼 수 없도록, 제출 성공 또는 운영진의 초기화 조작 이후 입력 데이터를 제거한다.

### 5.6. 제출 완료

**FR-W04. 완료 화면**

- 제출 성공 안내
- 관리자 검토 후 공개될 수 있음을 안내
- 메인으로 돌아가기
- 새 글 작성하기

제출 완료는 DB 저장 성공을 의미하며, 공개 승인을 의미하지 않는다.

---

## 6. 데이터베이스 설계

### 6.1. 기본 구조

데이터베이스는 Cloudflare D1을 사용한다.

초기 버전에서는 `letters` 테이블 하나를 사용한다.

### 6.2. letters 테이블

| 필드 | 자료형 | 조건 |
|---|---|---|
| `id` | TEXT | PRIMARY KEY |
| `nickname` | TEXT | NULL 허용 |
| `content` | TEXT | NOT NULL |
| `published_content` | TEXT | NULL 허용 |
| `consent_to_publish` | INTEGER | NOT NULL |
| `status` | TEXT | NOT NULL, 기본값 pending |
| `publish_order` | INTEGER | NULL 허용 |
| `submission_key` | TEXT | UNIQUE |
| `created_at` | TEXT | NOT NULL |
| `reviewed_at` | TEXT | NULL 허용 |

`id`는 UUID 기반으로 생성한다.

`created_at`과 `reviewed_at`은 UTC 기준으로 저장하고 한국 시간으로 표시한다.

### 6.3. 검수 상태

`status`는 다음 3가지 값만 허용한다.

| 값 | 의미 |
|---|---|
| `pending` | 검토 대기 |
| `approved` | 공개 승인 |
| `rejected` | 공개 제외 |

최초 제출 시 항상 `pending`으로 저장한다.

관리자만 상태를 변경할 수 있다.

### 6.4. 원문 보존

`content`는 제출 원문이다.

`published_content`는 운영진이 맞춤법 등을 수정한 공개용 글이다.

운영진이 공개용 내용을 수정하더라도 원문은 덮어쓰지 않는다.

공개용 내용이 비어 있으면 승인된 원문을 사용한다.

### 6.5. 공개 조건

다음 조건을 모두 만족하는 글만 공개할 수 있다.

- `status = approved`
- 공개 동의가 유효함
- 공개 가능한 본문이 존재함

그 외 자료는 일반 사용자에게 반환하지 않는다.

## 7. 백엔드 API 명세

모든 API의 데이터 형식은 JSON을 기본으로 한다.

### 7.1. POST /api/letters

**목적:** 새로운 홍보 글 저장

요청 항목:

| 필드 | 타입 | 필수 |
|---|---|---|
| `nickname` | string | 아니오 |
| `content` | string | 예 |
| `consentToPublish` | boolean | 예 |
| `submissionKey` | string | 예 |
| `turnstileToken` | string | 보안 기능 활성화 시 |

처리 조건:

- 서버에서 길이 및 형식 검증
- 공개 동의 검증
- 제출 기간 확인
- 중복 요청 확인
- 정상 요청만 DB 저장

성공 시 HTTP 201과 접수 ID를 반환한다.

동일한 제출 키로 재전송되면 기존 접수 결과를 반환할 수 있어야 한다.

### 7.2. GET /api/admin/letters

**목적:** 제출 글 조회

관리자 인증 필수.

지원 기능:

- 페이지 단위 조회
- 작성일 정렬
- 검수 상태별 필터링
- 키워드 검색

### 7.3. PATCH /api/admin/letters/:id

**목적:** 제출 글 검수

관리자 인증 필수.

변경 가능 항목:

- `status`
- `published_content`
- `publish_order`

원문 `content`는 직접 수정할 수 없도록 한다.

### 7.4. GET /api/admin/export

**목적:** 데이터 내보내기

관리자 인증 필수.

지원 형식:

- CSV: 운영 및 검수 기록용
- JSON: 데이터 백업 및 공개 파일 생성용

전체 데이터 내보내기와 공개 승인된 글 내보내기를 구분한다.

### 7.5. API 공통 오류 처리

| 상황 | HTTP 상태 |
|---|---|
| 정상 생성 | 201 |
| 정상 조회·수정 | 200 |
| 잘못된 입력 | 400 |
| 인증되지 않음 | 401 |
| 권한 없음 또는 제출 종료 | 403 |
| 대상 없음 | 404 |
| 요청 제한 | 429 |
| 서버 오류 | 500 |

오류 응답에는 정해진 오류 코드와 사용자에게 표시할 메시지를 포함한다.

서버 내부 오류나 비밀키 등은 클라이언트에 노출하지 않는다.

## 8. 관리자 시스템

### 8.1. 인증

**FR-A01. 관리자 접근 제한**

관리자 화면과 관리자 API는 인증된 운영진만 사용할 수 있다.

최초 버전은 단일 관리자 권한을 기준으로 설계한다.

인증 수단은 배포 환경에 맞춰 최종 결정하되 다음 조건을 반드시 만족해야 한다.

- 관리자 인증정보를 프런트엔드 코드에 저장하지 않는다.
- 서버에서 인증 및 권한을 검사한다.
- 세션은 안전한 쿠키 방식 등으로 보호한다.
- 로그아웃 또는 세션 만료를 지원한다.
- 로그인 시도 횟수를 제한한다.
- 인증되지 않은 사용자는 관리자 API를 사용할 수 없다.

### 8.2. 제출 글 관리

**FR-A02. 검수 기능**

운영진은 다음 작업을 할 수 있어야 한다.

1. 전체 제출 글 확인
2. 개별 글 상세 조회
3. 승인
4. 제외
5. 승인 취소
6. 공개용 내용 수정
7. 공개 순서 조정

모든 상태 변경은 서버에 저장되어야 한다.

### 8.3. 자료 내보내기

**FR-A03. 데이터 백업**

관리자 화면에서 전체 데이터를 내려받을 수 있어야 한다.

내보내기 형식:

- 전체 데이터: JSON
- 검수 목록: CSV
- 입학식 공개 데이터: JSON

CSV 다운로드 시 한글이 정상적으로 표시되도록 인코딩을 처리한다.

엑셀에서 수식으로 해석될 수 있는 사용자 입력값에 대한 CSV 수식 삽입 방지도 적용한다.

## 9. 입학식 공개 페이지

### 9.1. 목적

2027학년도 천안오성고등학교 신입생이 입학식에서 QR코드를 스캔하여 선배들이 작성한 글을 열람한다.

### 9.2. 공개 방식

**FR-P01. 글 열람**

- 승인된 글만 표시
- 모바일 브라우저 지원
- 작성자 표시명 표시
- 글의 줄바꿈 유지
- 공개 순서 적용
- 로그인 없이 열람 가능

### 9.3. 데이터 배포

최초 구현에서는 **정적 JSON 배포 방식**을 채택한다.

운영 과정:

1. 운영진이 제출 글을 검수한다.
2. 승인된 글을 공개용 JSON으로 내보낸다.
3. 공개용 JSON을 사이트에 포함한다.
4. 새 버전을 배포한다.
5. 신입생은 `/welcome`에서 해당 파일을 읽는다.

이 방식은 입학식 당일 DB가 응답하지 않더라도 이미 배포된 글을 열람할 수 있다는 장점이 있다.

단, 공개 내용을 변경하려면 파일을 다시 생성하고 재배포해야 한다.

### 9.4. QR코드

- QR코드는 `/welcome`의 최종 공개 주소로 생성한다.
- 입학식 전에 QR코드를 생성하고 실제 스마트폰으로 테스트한다.
- QR 이미지 파일을 인쇄 가능한 형태로 보관한다.
- QR 발급 이후 공개 주소를 변경하지 않는 것을 원칙으로 한다.

공개 도메인과 실제 입학식 날짜는 추후 확정한다.

## 10. 보안 및 데이터 보호

### 10.1. 입력 검증

모든 사용자 입력은 클라이언트와 서버에서 각각 검증한다.

클라이언트 검증만으로 데이터 무결성을 보장하지 않는다.

서버에서는 SQL 파라미터 바인딩을 사용하고, 글 출력 시 HTML을 실행하지 않는 안전한 렌더링 방식을 사용한다.

### 10.2. 스팸 방지

다음 보호 수단을 적용한다.

- 요청 횟수 제한
- 제출 키를 이용한 중복 요청 처리
- 서버 측 데이터 검증
- 필요 시 Cloudflare Turnstile

Turnstile을 사용할 경우 서버의 Siteverify 검증을 필수로 수행한다.

### 10.3. 개인정보 최소화

- 주민등록번호, 전화번호 등은 수집하지 않는다.
- 작성자 별명은 선택사항으로 한다.
- 공개 동의와 개인정보 안내를 제공한다.
- 행사 운영에 불필요한 이용자 추적을 하지 않는다.
- 원본 데이터와 공개 데이터의 접근 범위를 구분한다.

### 10.4. 데이터 보존

홍보 글 원본은 최소한 입학식용 공개 파일 생성이 완료될 때까지 보존해야 한다.

DB 장애에 대비하여 정기적인 외부 백업이 필요하다.

Cloudflare D1의 시점 복구 기능만으로 수개월 전 자료까지 복원할 수 있다고 가정하지 않는다.

백업 주기 제안:

- 행사 당일: 행사 종료 직후 1회 이상
- 검수 기간: 중요한 검수 작업 이후
- 입학식 준비 완료: 최종 백업
- 운영 종료: 자료 정리 및 보유 기간 검토

백업 파일은 DB와 별도의 저장 위치에 보관한다.

## 12. 비기능 요구사항

### 12.1. 브라우저 호환성

개발 및 테스트 대상:

- Chrome
- Edge
- Safari

타자 대회는 물리 키보드가 연결된 PC 사용을 기준으로 한다.

홍보 글 작성 및 신입생 공개 페이지는 모바일 사용을 지원해야 한다.

### 12.2. 접근성

- 키보드만으로 주요 기능 조작 가능
- 입력란에 명확한 레이블 제공
- 제출 오류를 텍스트로 안내
- 입력 상태와 오타를 색상에만 의존하지 않고 구분
- 모바일 화면에서 가로 스크롤 없이 주요 기능 이용 가능

### 12.3. 코드 구조

기능을 다음 영역으로 분리한다.

- `typing/engine`: 한글 입력 판정
- `typing/scoring`: 타수·오타·점수 계산
- `typing/storage`: 대회 기록 저장
- `letters`: 홍보 글 작성
- `admin`: 관리자 기능
- `welcome`: 공개 글 열람
- `api`: 서버 API
- `shared`: 공통 타입·유틸리티

추후 디자인 변경을 쉽게 할 수 있도록 기능 로직과 렌더링 코드를 분리한다.

### 12.4. 로깅

서버에서는 다음 종류의 오류를 확인할 수 있어야 한다.

- DB 연결 및 쿼리 오류
- 잘못된 요청
- 인증 실패
- 제출 실패
- 내보내기 실패

로그에 제출 글의 전체 본문이나 관리자 비밀정보를 불필요하게 기록하지 않는다.

## 13. 테스트 명세

### 13.1. 타자 대회

**TC-T01** 정상적으로 문구를 완성하면 기록이 생성된다.

**TC-T02** 오타가 없는 경우 감점이 발생하지 않는다.

**TC-T03** 오타가 1개면 20점이 차감된다.

**TC-T04** 오타가 3개면 60점이 차감된다.

**TC-T05** 한글 조합 중 임시 문자 변화가 오타로 중복 계산되지 않는다.

**TC-T06** 오타 수정 과정이 확정된 감점 규칙과 일치한다.

**TC-T07** 정상적인 Backspace 작업만으로 오타가 증가하지 않는다.

**TC-T08** 문구가 정확히 완성되기 전에 종료되지 않는다.

**TC-T09** 붙여넣기를 통한 입력이 차단된다.

**TC-T10** 새로고침·페이지 이탈 후 미완료 기록이 공식 순위에 남지 않는다.

**TC-T11** 결과가 로컬 저장소에 정상적으로 기록된다.

**TC-T12** CSV로 내보낸 점수·순위가 화면과 일치한다.

### 13.2. 홍보 글

**TC-W01** 정상적인 글이 DB에 저장된다.

**TC-W02** 필수 조건을 충족하지 않는 글은 거부된다.

**TC-W03** 제출 성공 전에는 완료 화면이 표시되지 않는다.

**TC-W04** 서버 오류 시 작성 내용이 유지된다.

**TC-W05** 동일 요청을 재전송해도 중복 저장되지 않는다.

**TC-W06** 관리자만 검수 상태를 변경할 수 있다.

**TC-W07** 승인되지 않은 글은 공개되지 않는다.

**TC-W08** 공개용 글을 수정해도 원문이 보존된다.

**TC-W09** 승인된 글만 공개 JSON에 포함된다.

**TC-W10** 제출 종료 후 신규 글이 저장되지 않는다.

### 13.3. 입학식 공개

**TC-P01** QR로 공개 페이지에 접근할 수 있다.

**TC-P02** 스마트폰에서 글을 정상적으로 열람할 수 있다.

**TC-P03** 글의 줄바꿈과 한글이 정상적으로 표시된다.

**TC-P04** 승인되지 않은 글이 포함되지 않는다.

**TC-P05** DB 연결이 없어도 정적 공개 페이지가 작동한다.

**TC-P06** 새 공개 데이터 배포가 실패하면 이전 정상 버전으로 복구할 수 있다.

## 15. 미확정 사항

다음 항목은 현재 요구사항만으로 확정할 수 없으므로 구현 전 결정이 필요하다.

| 항목 | 현재 상태 |
|---|---|
| 대회 타자 문구 | 미정 |
| 정확한 타수 산정 기준 | 잠정안 |
| 수정된 오타의 감점 유지 | 잠정안 |
| 음수 점수 및 동점 처리 | 미정 |
| 참가 횟수 제한 | 미정 |
| 타자 대회 운영 기기 수 | 단일 기기 가정 |
| 상품 종류·지급 기준 | 미정 |
| 홍보 글 길이 제한 | 잠정안 |
| 작성자 표시 방식 | 잠정안 |
| 관리자 인증 방식 | 미정 |
| 사이트 이름·도메인 | 미정 |
| 행사 및 입학식 날짜 | 미정 |
| 공개 종료 및 데이터 삭제 시점 | 미정 |

미확정 사항은 임의로 확정하지 않는다.

특히 타수 산정 방식과 오타 판정은 순위와 상품 지급에 직접적인 영향을 주므로, 기능 개발 초기 단계에서 우선 확정한다.

## 16. 개발 범위 제외

최초 버전에서는 다음 기능을 구현하지 않는다.

- 타자 문구 관리자 편집
- 사용자 회원가입 및 일반 로그인
- 실시간 온라인 통합 순위표
- 타자 대회 기록의 서버 DB 저장
- 사진·동영상 첨부
- 댓글 및 좋아요
- AI 글 자동 생성·교정
- 실시간 채팅
- 푸시 알림
- 복잡한 통계 대시보드
- 디자인 중심 애니메이션

추후 필요성이 확인되면 별도로 추가한다.

## 17. 최종 완료 조건

프로젝트는 다음 조건을 모두 충족하면 기능 구현이 완료된 것으로 판단한다.

1. 참가자가 한글 문구를 입력하고 정확한 점수를 확인할 수 있다.
2. 오타 감점이 확정된 대회 규칙에 따라 계산된다.
3. 운영진이 참가 기록을 취합하고 상품 지급에 활용할 수 있다.
4. 홍보 글이 D1에 정상 저장된다.
5. 관리자가 제출 글을 조회·검수·내보내기 할 수 있다.
6. 승인되지 않은 글은 외부에 공개되지 않는다.
7. 입학식용 공개 페이지를 생성할 수 있다.
8. QR코드로 모바일에서 열람할 수 있다.
9. 데이터 백업과 복구가 가능하다.
10. 기능이 실제 배포 환경에서 정상 작동하며 필수 테스트를 통과한다.

**본 명세서는 기능 구현 기준 문서이며, 시각적 디자인은 별도 작업으로 진행한다.**
